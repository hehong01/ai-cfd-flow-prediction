# 03. Fluent CFD Automation

Automate the complete ANSYS Fluent workflow from a CFD-ready SpaceClaim geometry to converged multi-speed CFD outputs and wall-field CSV data.

```text
SCDOC
  ↓
Meshing
  ↓
Physics / boundary-condition setup
  ↓
5 / 8 / 10 m/s simulations
  ↓
CAS/DAT + wall-field CSV
```

This stage is the core CFD automation layer of the project. Rather than only launching Fluent, `scdoc_to_cfd.py` reproduces the validated meshing and solver workflow, adapts file paths for each geometry, monitors runtime progress, detects known geometry failures, and validates the generated outputs.

## Input / Output

The default data directories are managed by the repository-level `project_paths.py`.

```text
Input:
ai-cfd-data/03_spaceclaim/face_XXXX.scdoc

Fluent Case/Data:
ai-cfd-data/04_fluent/face_XXXX_05mps.cas.h5
ai-cfd-data/04_fluent/face_XXXX_05mps.dat.h5
ai-cfd-data/04_fluent/face_XXXX_08mps.cas.h5
ai-cfd-data/04_fluent/face_XXXX_08mps.dat.h5
ai-cfd-data/04_fluent/face_XXXX_10mps.cas.h5
ai-cfd-data/04_fluent/face_XXXX_10mps.dat.h5

Wall-field CSV:
ai-cfd-data/05_cfd_csv/face_XXXX_05mps.csv
ai-cfd-data/05_cfd_csv/face_XXXX_08mps.csv
ai-cfd-data/05_cfd_csv/face_XXXX_10mps.csv
```

Each completed geometry therefore produces **9 output files**:

```text
3 velocities × (CAS + DAT + CSV)
```

The large generated CAS/DAT/CSV files are kept outside the Git repository.

## Automation Overview

For each input SCDOC, the automated CFD sequence is:

```text
Import SCDOC
    ↓
Generate / improve surface mesh
    ↓
Apply Share Topology
    ↓
Create + update regions
    ↓
Normalize split wall zones
    ↓
Generate wall boundary layer
    ↓
Generate Poly-Hexcore volume mesh
    ↓
Switch to solution mode
    ↓
Assign boundary types and physical models
    ↓
Set thermal / flow conditions
    ↓
5 m/s
    → Hybrid Initialization
    → 100 iterations
    → CAS/DAT + CSV export
    ↓
8 m/s
    → Hybrid Initialization
    → 100 iterations
    → CAS/DAT + CSV export
    ↓
10 m/s
    → Hybrid Initialization
    → 100 iterations
    → CAS/DAT + CSV export
    ↓
Validate all outputs
```

## CFD Workflow

### 1. Geometry Import

The `.scdoc` generated by `02_spaceclaim` is imported into Fluent using the **Watertight Geometry** workflow.

The SpaceClaim geometry already contains the Named Selections:

```text
wall
inlet
outlet
farfield
```

These labels provide the geometric basis for the downstream boundary setup.

### 2. Surface Meshing

The recorded workflow generates a curvature/proximity-aware surface mesh and then applies **Improve Surface Mesh**.

Validated surface-mesh settings:

| Setting | Value |
|---|---:|
| Minimum size | `2.12779 mm` |
| Maximum size | `54.47142 mm` |
| Growth rate | `1.2` |
| Normal angle | `18°` |
| Cells per gap | `1` |

### 3. Share Topology and Region Update

After surface meshing, the workflow executes:

```text
Apply Share Topology
    ↓
Create Regions
    ↓
Update Regions
```

Validated Share Topology settings:

| Setting | Value |
|---|---:|
| Maximum gap | `1.063895 mm` |
| Join normal angle | `40°` |
| Relative tolerance | `0.1` |
| Attempts | `3` |
| Increment | `0.05` |
| Join mode | `Join Only` |

### 4. Wall-Zone Normalization

A geometry-dependent issue appeared after `Update Regions`: the single SpaceClaim label `wall` could be split by Fluent into multiple wall face zones.

In some cases the split was effectively:

```text
main facial wall
+
small 1-face wall-zone artifact
```

Discarding the smaller zone or simply selecting the largest zone would risk deleting valid mesh faces. The final automation therefore uses the SpaceClaim `wall` label itself as the source of truth.

The journal performs:

```text
find every Fluent face zone carrying label "wall"
    ↓
merge all wall-labelled face zones
    ↓
verify exactly one wall zone remains
    ↓
normalize its name / ID
    ↓
continue the validated journal
```

The normalized wall zone is:

```text
wall-zone------------:2030
```

### 5. Boundary-Layer Generation

Boundary layers are generated on the normalized facial wall.

| Setting | Value |
|---|---:|
| Method | `Smooth Transition` |
| Number of layers | `3` |
| Transition ratio | `0.272` |
| Growth rate | `1.2` |
| Grow on | `wall` |

### 6. Volume Meshing

The external flow domain is filled with a **Poly-Hexcore** volume mesh.

| Setting | Value |
|---|---:|
| Volume fill | `Poly-Hexcore` |
| Buffer layers | `2` |
| Peel layers | `1` |
| Minimum size | `2.12779 mm` |
| Maximum size | `34.04464 mm` |

After the mesh is generated, Fluent switches from meshing mode to solution mode.

### 7. Physical Models and Boundary Conditions

#### Physical models

| Model | Setting |
|---|---|
| Energy | `ON` |
| Viscous model | `SST k-ω` |

#### Inlet

| Setting | Value |
|---|---:|

| Velocity magnitude | `5 / 8 / 10 m/s` |
| Temperature | `268.15 K` |
| Turbulence intensity | `5 %` |
| Turbulent viscosity ratio | `10` |

#### Outlet

| Setting | Value |
|---|---:|
| Type | `pressure-outlet` |
| Gauge pressure | `0 Pa` |
| Backflow temperature | `268.15 K` |

#### Facial wall

| Setting | Value |
|---|---:|
| Type | `wall` |
| Momentum condition | `no-slip` |

#### Farfield

```text

```

### 8. Solver Settings

| Setting | Value |
|---|---|

Each velocity is reinitialized independently before calculation:

```text

    ↓
Hybrid Initialization
    ↓
100 iterations
    ↓
Export 05mps CAS/DAT + CSV

8 m/s
    ↓
Hybrid Initialization
    ↓
100 iterations
    ↓
Export 08mps CAS/DAT + CSV

10 m/s
    ↓
Hybrid Initialization
    ↓
100 iterations
    ↓
Export 10mps CAS/DAT + CSV
```

### 10. Result Export and Validation

For each velocity, Fluent writes:

```text
Case & Data
+
wall-surface CSV
```

The expected CSV schema contains exactly 10 columns:

```text
nodenumber
x-coordinate
y-coordinate
z-coordinate
pressure
temperature
y-plus
wall-shear
heat-flux
heat-transfer-coef
```

`scdoc_to_cfd.py` validates that:

- each CAS file exists and is non-empty,
- each DAT file exists and is non-empty,
- each CSV exists and is non-empty,
- the CSV header matches the expected 10-column schema,
- the CSV contains data rows,
- the `x`, `y`, and `z` coordinate columns are not duplicated.

## Automation Architecture

### Journal-Based Fluent Automation

The initial reconstruction attempted to reproduce the full Fluent workflow through direct API/TUI automation.

In Fluent 2021 R1, reproducing the exact successful workflow only through individually reconstructed API calls was difficult to validate reliably. Version-specific workflow objects and GUI-driven settings also made it easy for the automated setup to diverge from the manually verified configuration.

The final approach therefore uses a **recorded successful Fluent journal as the source of truth**:

```text
manually validated Fluent workflow
    ↓
recorded journal
    ↓
minimal controlled modifications
    ↓
runtime path substitution
    ↓
automated Fluent execution
```

Python handles orchestration, path substitution, monitoring, diagnostics, and output validation, while the journal preserves the validated Fluent setup.

### Embedded Journal and Reference Journal

`scdoc_to_cfd.py` contains the validated Fluent journal directly as:

```text
EMBEDDED_JOURNAL
```

The script therefore does not require a separate `.jou` file during normal execution.

The repository also retains:

```text
fluent_cfd_workflow.jou
```

as a reference/provenance copy of the recorded workflow.

An external journal can still be supplied with `--journal`.

### Runtime Path Substitution

Before Fluent is launched, the script substitutes:

- the input SCDOC path,
- three Case/Data output paths,
- three CSV output paths.

A face-specific journal is generated under:

```text
03_fluent_cfd/_runs/<face>_<timestamp>/
```

### Runtime Monitoring

On Windows, `fluent.exe` acts as a launcher, so the launcher process alone does not prove that the full calculation has completed.

The script therefore monitors all expected generated files and waits until:

```text
all 9 outputs exist
+
their file sizes stop changing
```

while also polling the Fluent transcript for known failures.

### Transcript-Based Diagnostics

Each run creates a Fluent transcript (`.trn`) in its run directory.

If a failure occurs, the diagnostic routine associates the error with the most recent journal command echoed by Fluent. This makes the failing Fluent operation visible instead of relying only on Python-side errors.

### Validated Geometry Fallback

The standard SpaceClaim preprocessing uses a **5.0 mm Shrinkwrap**.

During full-pipeline validation, two geometries in the 100-case batch failed at Fluent `Apply Share Topology`; the transcript reported tens of thousands of self-intersecting triangles.

The same STL geometries were regenerated while changing only the Shrinkwrap resolution:

```text
5.0 mm → 4.0 mm
```

Both then completed the full CFD workflow successfully.

The production pipeline therefore uses the targeted fallback:

```text
5 mm SCDOC
    ↓
run Fluent
    ↓
Share Topology self-intersection detected?
    │
    ├─ No → continue normally
    │
    └─ Yes
         ↓
       scdoc_to_cfd.py returns exit code 42
         ↓
       master_run.py rebuilds only that geometry at 4 mm
         ↓
       retry Fluent once
```

The fallback is only triggered for the specific transcript-detected Share Topology self-intersection condition.

## Automation Development Notes

### 1. Direct API Reconstruction → Recorded Journal

**Problem**

Reconstructing the complete successful Fluent workflow as independent API/TUI calls introduced too many version-specific and GUI-dependent details to verify confidently in Fluent 2021 R1.

**Resolution**

A manually successful workflow was recorded as a Fluent journal and used as the automation backbone. Python was then limited to the surrounding automation tasks that could be validated independently.

### 2. Geometry-Dependent Wall-Zone Split

**Problem**

After `Update Regions`, some geometries retained one facial wall zone while others produced multiple zones, including a small 1-face artifact.

A naive "keep the largest wall zone" rule could discard legitimate mesh faces.

**Resolution**

All zones associated with the SpaceClaim `wall` label are queried and merged. The script then verifies that exactly one wall zone remains before continuing.

### 3. Share Topology Self-Intersection at 5 mm

**Problem**

The 100-geometry batch exposed cases in which the normal 5 mm Shrinkwrap SCDOC reached Fluent successfully but failed during `Apply Share Topology`.

**Resolution**

Transcript polling detects the combination:

```text
self-intersecting triangles
+
Apply Share Topology
```

and returns dedicated exit code `42`.

`master_run.py` rebuilds only the failed SCDOC at 4 mm and retries Fluent once.

### 4. Duplicate Coordinate Columns in CSV Export

**Problem**

The original recorded 5 m/s export contained an extra CSV export in which `x`, `y`, and `z` were selected again as exported physical quantities. Since Fluent already writes coordinate columns, this produced duplicate coordinate fields.

**Resolution**

The redundant export was removed and the quantity selection was corrected so that each speed produces one consistent 10-column CSV.

The validator also explicitly detects duplicated coordinate columns.

### 5. Journal Output-Name Normalization

The recorded 10 m/s Case & Data filename used a different extension pattern from the 5 and 8 m/s outputs.

The automated journal normalizes it to:

```text
.cas.h5
```

so that all three velocity cases use the same naming convention.

## Usage

Run from the repository root.

### Dry-run

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --face face_0001 --dry-run
```

If outputs already exist:

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --face face_0001 --dry-run --overwrite
```

### Run one geometry

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --face face_0001 --overwrite
```

### Validate existing outputs only

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --face face_0001 --check-only
```

### Diagnose the latest Fluent transcript

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --diagnose
```

### Save the embedded journal

```powershell
python .\03_fluent_cfd\scdoc_to_cfd.py --save-journal exported_workflow.jou
```

### Main command-line options

| Option | Default | Description |
|---|---:|---|
| `--face` | script default | Face/case ID to process |
| `--fluent-exe` | v211 path | Fluent executable |
| `--journal` | embedded journal | Use an external journal |
| `--nproc` | `4` | Number of Fluent processes |
| `--overwrite` | off | Delete existing outputs before running |
| `--timeout` | script timeout | Maximum wait time |
| `--dry-run` | off | Prepare the journal without launching Fluent |
| `--check-only` | off | Validate existing outputs only |
| `--no-auto-exit` | off | Leave Fluent open when the journal finishes |
| `--no-wait` | off | Launch without waiting for outputs |
| `--diagnose` | off | Diagnose the latest Fluent transcript |
| `--save-journal` | — | Export the embedded journal |

## Output Data

The wall CSV is the raw CFD input for `04_cfd_dataset`.

| Category | Fields |
|---|---|
| Index | `nodenumber` |
| Geometry | `x-coordinate`, `y-coordinate`, `z-coordinate` |
| Flow | `pressure` |
| Thermal | `temperature`, `heat-flux`, `heat-transfer-coef` |
| Wall / turbulence-related | `y-plus`, `wall-shear` |

Because the wall mesh is generated independently for each geometry, the number of wall nodes can vary between faces.

The validated batch contains:

```text
100 geometries × 3 velocities = 300 CFD samples
```
